# mb-doc-maintainer — Complete Consolidated Plan

**Status:** Final. All decisions locked. No open questions. No open issues.

---

## 1. Purpose

`mb-doc-maintainer` maintains documentation integrity at save time: when a document is saved, ensure the affected documentation remains compliant with the documented requirements of G-brain, structurally coherent, correctly registered, and usable by G-brain — doing the minimum work necessary (Spec §2).

**What it is not:** an auditor, corpus-cleaning system, document-management system, or replacement for `mb-doc-auditor` (Spec §1).

**Standing boundaries:**

- **DocCycle** — never reused, incorporated, adapted, extracted, modified, dismantled, migrated, refactored, or retired. Completely separate and untouched. Not a question; the answer is established.
- **mb-doc-auditor** — excluded from this work entirely; not designed, built, or referenced.
- **The developer is not the maintenance system** — human attention is reserved for genuine judgement calls only.

**Governing principle (Spec §21):** Maintain the saved change against the known requirements of G-brain, repair what can be safely repaired, ask only when judgement is genuinely required, and then stop.

## 4. Skill specification (Phase 2 output)

**Artifact:** `C:\mybizz\mb-doc-maintainer\SKILL.md` in source repo `C:\mybizz\mb-doc-maintainer\` (git init, GitHub-backed per ADR `adr-dev-tooling-source-repos-must-be-github-backed`).

Structure follows the supplied specification's own sections:

1. **Governance header** — Spec §18 prohibition list verbatim plus the §21 governing principle, placed first in the file as point-of-action rules. Prohibitions: no full-corpus audit after every save; no perfecting the estate; no searching for unrelated problems; no processing historical inconsistencies; no work from mere difference; no invented G-brain requirements; no invented semantic relationships; no guessing when uncertain; no large routine reports; no approval demands for safe mechanical repairs; no register bureaucracy; no repeated rescans; no becoming a document-management system; no duplicating the auditor; no becoming a smaller DocCycle.
2. **Trigger model** (Spec §4) — invocation drains the pending-events queue; operates on saved state only; never follows live editing; empty queue = nothing to do. Rapid saves coalesced upstream (D8) so intermediate states are never processed.
3. **Scope rules** (Spec §5) — the saved document, its directly affected references, files directly affected by a move/rename, links affected by the change, the applicable register. Scope authority read live (D6). A local change never expands into a corpus-wide investigation. Core principle: maintain what changed, not everything that exists.
4. **Event handlers** (Spec §6–§9):
   - **Creation** — set frontmatter to exactly `title:` + `doc-id:` (O1/D2 exclusivity — no other fields); ensure correct location; validate references; convert applicable references to wikilinks; verify targets exist; register the document (D5).
   - **Modification** — inspect changes and affected relationships; check only requirements relevant to the change; restore frontmatter to exactly `title:` + `doc-id:`, deleting any other field that appears; repair affected links; convert appropriate references to wikilinks; update registration; restore any directly affected invariant.
   - **Move/Rename** — identify directly affected references and register rows; apply mechanically determinable updates; update the register (rename event); verify affected links and the new location; ambiguity → ask the developer, never guess.
   - **Deletion** — remove the register row; identify affected references; repair where the correct replacement is known; report unresolved references for human decision; never invent replacement documents or relationships.
5. **Link rules** (Spec §10) — target exists; reference points to the intended document; required wikilink form per O6/G6; a link that resolves is not automatically semantically correct — unresolvable semantic correctness → human judgement, never invented.
6. **Register maintenance** (Spec §11 + D4/D5) — register determined from the document's project/library context (register-local per project library, register-global for project-library-global); four-event model; mechanical updates automatic; never a separate approval bureaucracy; undeterminable registration → ask.
7. **Classification** (Spec §12) — every finding falls into exactly one of: **Must fix** (violates a contract requirement or creates a concrete integrity problem — repair automatically where safe) / **Can wait** (real but not part of this event — never a new work queue) / **Doesn't matter** (no meaningful impact — no action) / **Requires human judgement** (cannot safely determine the action — concise decision request).
8. **Automation boundary** (Spec §13) — act automatically only when all of: explicitly supported by the contract, mechanically determinable, safe, verifiable. Human input required when: semantic relationship ambiguous, multiple valid repairs, destructive decision required, requirement unclear, action would invent information. Never guess merely to avoid asking.
9. **Reporting** (Spec §14–§16) — concise summary in the spec's example format (Saved: X / Actions / Status); decision format Issue / Proposed action / Risk / Approve–Reject when judgement is needed; detail available on request (query the result: what was checked, what changed, what was decided not to need changing, which requirement caused a change); summary by default, detail on request; never a large report to discover nothing important needs attention.
10. **Processing loop** (Spec §17) — identify change → determine affected G-brain requirements → determine affected documentation → repair what can be safely repaired → update required registration → verify → summarise → **FINISH**. The process must terminate. Detection is not a work queue; finding additional differences does not justify continuing.
